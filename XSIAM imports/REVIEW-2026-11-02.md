## Tenant: the correlation engine is down, and XQL with it

- **Zero correlation alerts since 2026-10-14 10:09.** All 110 rules are enabled.
- The XQL API refuses new queries with `reached max allowed amount of parallel running
  queries`. Over ~2 h, `total_daily_running_queries` moved 1482 → 1485 while rejections
  climbed to 40+. The few queries that did start returned `FAIL` with no error and zero
  cost.
- Nothing in LogSim issues XQL on a loop (the dashboard and MCP servers do not use
  `XsiamClient`), so the jam is tenant-side.
- Scheduled correlation rules run as XQL, so this is the most likely cause of the
  outage. Check the Query Center for stuck queries and cancel them; failing that, open a
  ticket with Palo Alto. Until it clears, no rule can be proven to fire.

### Delete-and-reload, 2026-11-02 (did not clear the jam)

All 125 rules were exported (`tenant_export_2026-11-02.json`), checked field-for-field
against the tenant, deleted one at a time with each deleted id confirmed, and recreated
by `integrations/correlation_rules_reload.py`. The old → new id map is in
`reload_ledger_2026-11-02.json`, and `rule_ids.json` now holds the new ids.

- 124 rules came back identical to the export.
- Rule 80 "Zscaler - Identify Hosts with Anomalous Firewall Denies" (disabled) was
  rejected on insert: its `fields -` exclusion selects 77 columns against the 50-column
  `addrawdata` cap. The tenant had kept it from before validation. It was restored, still
  disabled, with the 15-column `fields` list from de5e809, which had never been deployed.
- **The jam did not clear.** With zero rules in the tenant, XQL accepted queries again,
  but none completed within 2 minutes, and within ~10 minutes the parallel-query cap was
  back. The correlation rules are not what holds the slots. The fix is tenant-side: cancel
  stuck queries in the Query Center, or open a Palo Alto support case.

## Needs a decision — rule design

- **Duplicates that double-alert one event:** 1649 ≡ 1650 (identical queries, and 1644 is a
  superset of both); 1583 ≡ 1614. Suggest disabling 1650 and 1583.
- **Web C2 beacon, two versions per vendor (1668–1675, 8 rules):** v1 has the
  uncommon-domain logic, v2 has the entity mapping. v2 dropped the domain filter and
  will fire on ordinary browsing (≥8 hits to any one domain in 15–30 min). Suggest merging
  v1's filter into v2 and disabling v1.
- **1600 Okta multiple external IPs** is filed as scenario 2 step 5 but needs ≥3 IPs; the
  scenario logs in once. 1645 is the rule that actually covers that step.
- **1645 Okta victim external login** has no phishing correlation and no suppression; it
  fires on every external login.
- **119 Proofpoint / Okta** joins click IP = Okta login IP, which matches a user logging in
  from their own workstation after any permitted click. 121 (sender IP = login IP) is the
  one that matches scenario 2's design.
- **"CUSTOM mapping needs `| fields`"** is not the real rule: 1645 has no `fields` and fired
  8×. The likely real constraint is the 50-column `addrawdata` cap, which the datamodel
  Proofpoint rules (1642/1643/1647/1648, ~37 aliases plus all `xdm.*`) probably exceed.
  Verify once XQL works.
